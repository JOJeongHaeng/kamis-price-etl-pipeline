# SmartShopping 가격 조회 웹서비스 설계

작성일: 2026-08-23
상태: 검토 대기
목표: K-TCB IT개발/웹개발 전환형 인턴 지원용 웹 MVP

## 1. 목적

SmartShopping은 KAMIS 공공 API와 기존 XLSX/PDF 가격 자료를 수집·정제·저장하고, 사용자가 농산물 가격을 웹에서 검색하고 비교할 수 있게 하는 데이터 기반 웹서비스다.

이번 작업은 기존 ETL 파이프라인을 교체하지 않는다. 이미 적재된 가격 스냅샷을 제공하는 웹 계층을 추가해 외부 데이터 수집, 관계형 데이터 모델링, REST API, 서버 렌더링 UI, 오류 처리, 자동 테스트까지 하나의 실행 가능한 서비스로 연결한다.

## 2. 성공 기준

- 별도 KAMIS 인증키나 MySQL 없이 SQLite 데모 모드로 실행할 수 있다.
- 사용자가 웹 화면에서 품목명과 시장 구분으로 최신 가격을 검색할 수 있다.
- 같은 검색 결과를 JSON REST API로 받을 수 있다.
- 가격, 단위, 조사일, 도매·소매 구분, 데이터 신선도를 확인할 수 있다.
- 페이지네이션, 빈 결과, 잘못된 입력, DB 장애가 일관되게 처리된다.
- 기존 MySQL 기반 ETL 및 적재 구조를 유지한다.
- 신규 기능은 자동 테스트와 기능 단위 Git 커밋으로 검증된다.

## 4. 아키텍처

```text
Browser
  |-- GET /                  HTML price search
  `-- GET /api/prices        JSON price search
              |
              v
         PriceService
              |
              v
        PriceRepository
              |
              v
     SQLite demo / MySQL
```

웹 라우트와 API 라우트는 같은 `PriceService`를 사용한다. 검색 쿼리는 `PriceRepository`에만 위치시켜 데이터베이스 접근과 HTTP 표현을 분리한다. 기존 ETL은 웹 요청과 독립적으로 데이터를 수집하고 적재한다.

예상 파일 구조는 다음과 같다.

```text
web/
  __init__.py
  app.py
  database.py
  repository.py
  schemas.py
  service.py
  templates/
    index.html
  static/
    styles.css
tools/
  seed_demo_db.py
tests/
  test_web_repository.py
  test_web_api.py
  test_web_pages.py
```

구현 중 더 작은 구성이 충분하면 파일을 합칠 수 있지만, HTTP·업무 규칙·DB 접근 경계는 유지한다.

## 5. 데이터 소스와 호환성

애플리케이션은 `DATABASE_URL` 환경변수로 연결 대상을 선택한다.

- 환경변수가 있으면 해당 SQLAlchemy 연결 문자열을 사용한다.
- 환경변수가 없으면 프로젝트 내부 SQLite 데모 DB를 사용한다.
- SQLite 데모 DB는 별도 초기화 명령으로 생성하며 생성된 DB 파일은 Git에 커밋하지 않는다.
- 샘플 데이터 정의는 재현 가능한 소스 파일 또는 초기화 코드로 관리한다.

웹 조회 모델은 기존 `KAMISPriceAnalysis` View가 제공하는 의미를 따른다. SQLite에서는 호환 가능한 조회 또는 쿼리 표현으로 같은 필드를 반환한다.

필수 응답 필드는 다음과 같다.

- `item_name`
- `variety_name`
- `product_cls_name` 또는 시장 구분명
- `grade_name`
- `unit`
- `unit_size`
- `price`
- `examined_date`
- `freshness_status`

## 6. HTTP 인터페이스

### 웹 화면

`GET /`

쿼리 매개변수:

- `q`: 품목명 부분 검색, 선택
- `market_type`: `retail` 또는 `wholesale`, 선택
- `page`: 1 이상의 정수, 기본값 1

화면은 검색 폼, 결과 건수, 가격 목록, 신선도 배지, 페이지 이동을 제공한다. 검색 결과가 없으면 정상 화면 안에 안내 문구를 표시한다.

### REST API

`GET /api/prices`

웹 화면과 같은 검색 조건에 `page_size`를 추가한다. `page_size`는 기본 20, 최대 100으로 제한한다.

성공 응답 구조:

```json
{
  "items": [],
  "page": 1,
  "page_size": 20,
  "total": 0,
  "total_pages": 0
}
```

목록은 조사일 내림차순, 품목명 오름차순의 안정적인 순서를 사용한다.

## 7. 신선도 규칙

기존 프로젝트 규칙을 그대로 사용한다.

- `FRESH`: 조회 기준일로부터 30일 이내
- `CAUTION`: 30일 초과 1년 이내
- `STALE`: 1년 초과

DB View가 신선도를 제공하면 그 값을 사용한다. SQLite 호환 조회에서는 서비스 또는 쿼리 계층이 같은 경계값으로 계산한다. 테스트는 30일과 1년 경계값을 명시적으로 검증한다.

## 8. 오류 처리와 로깅

- 잘못된 페이지, 페이지 크기, 시장 구분은 FastAPI 검증 오류인 HTTP 422로 응답한다.
- 결과 없음은 오류가 아니며 HTTP 200과 빈 목록을 반환한다.
- DB 조회 실패 시 API는 HTTP 503과 고정된 안전한 오류 코드를 반환한다.
- 웹 화면은 내부 예외나 연결 문자열을 노출하지 않고 서비스 이용 불가 안내를 표시한다.
- 서버 로그에는 예외 원인과 요청 경로를 남기되 인증정보와 DB 비밀번호는 기록하지 않는다.
- 데이터 보정은 웹 계층에서 수행하지 않는다. 유효하지 않은 데이터는 ETL 품질 관리 범위로 남긴다.

## 9. UI 원칙

단일 반응형 화면으로 구현한다. 채용 포트폴리오에서 코드와 동작을 빠르게 평가할 수 있도록 시각 효과보다 정보 구조를 우선한다.

- 상단: 프로젝트 설명과 데이터 기준일 안내
- 검색 영역: 품목명, 시장 구분, 검색 버튼
- 결과 영역: 품목, 품종, 시장, 등급, 단위, 가격, 조사일, 신선도
- 상태 영역: 빈 결과 또는 서비스 오류 안내
- 모바일에서는 표를 가로 스크롤하거나 카드형으로 읽을 수 있게 한다.

접근성을 위해 명시적인 입력 라벨, 키보드 포커스, 충분한 색상 대비를 사용하고 신선도를 색상만으로 전달하지 않는다.

## 10. 테스트 전략

모든 동작 변경은 실패하는 테스트부터 작성한다.

### 저장소와 서비스

- 품목명 부분 검색
- 시장 구분 필터
- 안정적인 정렬
- 페이지네이션과 전체 건수
- 신선도 경계값

### REST API

- 기본 목록 응답 스키마
- 검색 및 필터 전달
- 잘못된 입력의 HTTP 422
- 빈 결과의 HTTP 200
- DB 장애의 HTTP 503과 안전한 오류 본문

### 웹 화면

- 검색 폼과 결과 렌더링
- 쿼리 값 유지
- 빈 결과 안내
- DB 장애 안내와 내부정보 비노출

### 회귀 검증

- 기존 ETL 테스트 전체
- 신규 웹 테스트 전체
- 애플리케이션 시작과 SQLite 데모 초기화 명령

## 11. 기능별 커밋 경계

1. `chore: stabilize Python test environment`
   - 재현 가능한 테스트 명령과 줄끝 정책
2. `feat: add price query repository and service`
   - SQLite 연결, 데모 초기화, 조회 서비스와 테스트
3. `feat: expose price search REST API`
   - API 스키마, 검증, 오류 처리와 테스트
4. `feat: add price search web page`
   - Jinja2 화면, 스타일, 화면 테스트
5. `docs: present SmartShopping web service`
   - 실행 방법, 아키텍처, API 예시, 화면 캡처

각 커밋 직전에 해당 기능 테스트와 전체 테스트를 새로 실행한다. 기존 작업 트리의 줄끝 변경은 의미 있는 변경과 섞지 않는다.

## 12. 완료 조건

- 깨끗한 환경에서 의존성을 설치하고 테스트를 실행할 수 있다.
- SQLite 데모 DB를 초기화하고 FastAPI 서버를 실행할 수 있다.
- 브라우저와 REST API에서 동일한 검색 결과를 확인할 수 있다.
- 전체 테스트가 통과한다.
- 비밀정보와 생성된 DB가 Git에 포함되지 않는다.
- README만으로 프로젝트 목적, 구조, 실행법, 핵심 기술 선택을 이해할 수 있다.
